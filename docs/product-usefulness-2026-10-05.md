# Rescue Meal 사용 흐름 개선 — 2026-10-05

## 서비스의 약속

사용자가 매일 모든 식품을 관리하게 만드는 대신, 오늘 필요한 결정을 돕는다.
‘집에 무엇이 있지?’ → ‘무엇을 만들 수 있지?’ → ‘무엇만 더 사면 되지?’ → ‘얼마나 썼지?’가 이어져야 한다.
음식의 안전 여부나 확인하지 않은 소비기한, 금전 절약 성과를 만들어 내지 않는다.

## 이번에 구현한 개선

| 사용 순간 | 이전의 부담 | 구현한 동작 | 완료 기준 |
|---|---|---|---|
| 처음 열었을 때 | 영수증을 준비해야 시작하는 것처럼 보임 | 첫 식품은 이름·수량·보관 위치를 직접 입력. 여러 상품은 별도 영수증 진입 | 빈 재고 → 직접 입력 → 첫 기록 → 홈에서 해당 식품 확인 |
| 장보기 전 | 전체 목록을 찾아 내려가 필터를 설정 | 홈의 냉장·냉동·실온별 개수에서 해당 목록 바로 열기 | 이전 검색어·상태 필터 초기화, 선택한 위치만 표시 |

| 메뉴를 고른 다음 | 저장·조리 방법 버튼을 찾으려면 긴 화면 이동 | 재료 요약 바로 아래 저장·조리 방법 배치 | 저장은 수량을 바꾸지 않으며 실제 조리 완료에서만 사용량 차감 |
| 재료를 장보기에 추가 | 집에 이미 있는 수량을 놓치기 쉬움 | 같은 정규화 이름의 보관 기록을 수량·위치별로 표시 | 유사 이름을 같은 상품이라고 단정하지 않고 수량·단위를 임의 합산하지 않음 |
| 구매한 식품 등록 | 수량 단위 누락, 냉장 기본 선택, 큰 소수 입력 실패 | 수량 옆 단위, 명시적 보관 선택, 저장할 내용 요약 | 구매 확인 및 보관 선택 전 저장 불가. 1000.5g 그대로 입력·저장 |
| 장보기 중 다른 기기에서 변경 | 예전 재고량을 현재 보유량처럼 안내 | 장보기 새로고침에 재고도 갱신. 실패 시 보유량 안내 숨김 | 수량 갱신·실패 처리 중 입력 초안 유지 |
| 이전에 저장한 식단 사용 | 엄격해진 시간 조건으로 과거 식단의 장보기 재계산 실패 | 저장된 동일 메뉴의 재계산에는 저장된 실제 조리시간 허용 | 과거 식단도 부분 구매 후 잔량 갱신, 전량 구매 후 부족 항목 제거 |
| 체험판 사용 | ‘게스트’가 실제 저장 계정처럼 보임 | ‘체험 중’과 새로고침 시 초기화 안내 | 예시 데이터와 실제 연결 상태를 구별 |

## 화면에서 확인한 범위

1. 기존 홈: 목록과 행동의 위치를 확인하고 화면을 기록했다.
2. 기존 식단: 저장·조리 방법이 긴 설명 뒤에 위치한 것을 확인했다.
3. 기존 등록: 영수증 기본 진입과 직접 입력 탭을 확인했다.
4. 개선한 홈: 모바일에서 식단 버튼, 보관 위치별 진입, 날짜 안내의 배치와 밝은/어두운 테마를 확인했다.
5. 개선한 식단: 메뉴 요약 옆 저장·조리 방법, 10분 선택 후 실제 10분 메뉴를 확인했다.
6. 개선한 장보기: 기존 보유량 펼치기, 구매 확인, 보관 선택 전 비활성, 수량·단위·보관 요약을 확인했다.

화면 캡처는 [이번 실행 기록](../evidence/usefulness-2026-10-05/)에 있다. 로컬의 별도 테스트 API와 데이터베이스를 사용했다.

## 실제 사용자에게 확인할 기준

아래는 다음 사용자 관찰의 기준이며 측정된 성과가 아니다.

- 설명 없이 첫 식품을 등록할 수 있는가. 중도 포기한 입력 항목은 무엇인가.
- 장보기 전에 보유량을 찾고, 중복해서 사려던 품목을 스스로 발견하는가.
- 조리 시간·인원에 맞는 메뉴를 얻는가. 실패 안내 뒤 사용자가 다음 행동을 선택할 수 있는가.
- 조리 후 실제 사용량을 기록하는가. 단위 때문에 기록을 포기하지 않는가.
- 다음 날 앱을 다시 열어 식품을 확인할 이유가 생기는가.

기존 승인 scorecard의 점수는 실제 사용자·운영 증거 없이 올리지 않는다.

## 후속 개선: 반복 입력과 이동 줄이기

사장님의 ‘더 편리하게 느껴지도록’ 요청에 맞춰 다음 동작을 추가했다.

| 개선 | 이전 | 이후 |
|---|---|---|
| 장보기 진입 | 홈의 장보기 영역까지 이동 | 하단 장보기 메뉴에서 바로 진입, 닫으면 원래 화면으로 복귀 |
| 같은 식품 다시 입력 | 이름을 다시 타이핑 | 현재 식품 목록에서 이름을 최대 4개 선택. 상품 정보·날짜는 복사하지 않음 |
| 수량 단위 입력 | 숫자와 단위를 직접 타이핑 | 개·팩·모·g·ml 버튼. 숫자는 유지하며 단위를 환산하지 않음 |
| 일부만 사용 | 500g → 250g는 −1 버튼 250회, 1팩은 일부 선택 불가 | 절반·전체·직접 수량 입력. 1팩 → 0.5팩도 가능 |
| 식단에서 안 쓴 재료 | 키보드로 0을 입력하거나 반복 감소 | ‘이번엔 안 씀’ 한 번, ‘다시 사용’으로 직전 양 복원 |

수량 선택은 초안만 바꾼다. 저장·소비·폐기는 유효한 양을 확인한 뒤 기존 실행 경로에서 처리한다. 빈 값, 0, 보유량 초과, 허용 정밀도를 벗어난 값은 실행하지 않는다. 0/NaN이 전체 소비로 해석되던 호출부의 가능성도 차단했다. 천 단위 쉼표와 `.5kg` 입력을 일관되게 읽고, 소수 차감 후 부동소수점 잔여 숫자가 재고에 남지 않게 했다.

식단 제외·복원은 레시피와 기록 공간별로 기억하며, 새 식단에 이전 수량·안전 확인·실패한 완료 요청이 섞이지 않는다. 모든 재료를 제외하면 완료할 수 없다. 날짜 확인 및 실제 먹은 기록의 확인 단계는 유지한다.

후속 검증 결과:

- 수량·수동 입력·식단 선택의 순수 로직 테스트 **17 passed**.
- 새 편의 기능 브라우저 테스트 **4 passed**: 장보기 왕복, 이름·단위 초안, 1팩 절반 및 확인 단계, 식단 제외·복원/전체 제외 차단.
- API 연결 테스트 **2 passed**: `500g → 250g 사용 → 250g 남음`, `.5kg → .2kg 사용 → .3kg 남음`의 재조회·새로고침 지속성과, 식단 제외 항목의 소비량 0 전송·재고 보존.
- 기존 사용성 브라우저 회귀 **3 passed**.
- 접근성 검사 **2 passed**: 홈 320/393px 밝은·어두운 테마 및 식품 상세.
- 좁은 웹 화면 **1 passed**: 320px에서 하단 메뉴 4개가 화면 안에 들어오며 터치 영역 44px 이상.
- 최신 TypeScript/Vite 빌드, 보호 모바일 런타임 28개, `git diff --check` 통과.

실제 브라우저에서는 입력 전/이름·단위 선택 후/절반 수량 선택/식단 재료 제외/장보기 하단 메뉴를 확인했다. [후속 화면 기록](../evidence/convenience-2026-10-05/)에 저장했다. 식단 제외 캡처는 자동 요소 이동 과정에서 시트 제목이 일부 잘린 상태이므로 전체 화면 배치의 증거로 사용하지 않는다. 수동 입력·수량 선택·홈 캡처는 화면을 직접 확인했다.

기존의 전체 회귀 실패 목록과 실기기·운영 배포 미검증 범위는 그대로 남는다. 이번 통과 결과를 전체 운영 검증으로 확대하지 않는다.
