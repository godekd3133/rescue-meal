# 영수증 가능성 Spike — 2026-09-01

## 결론

제공된 영수증 사진 3장은 영수증 기반 재고 `초안`을 만들기에 충분한 텍스트를 포함합니다. 그러나 수량 누락, 날짜 오인식, 할인 라인, 내부 상품코드, 겹친 카드전표가 확인되어 검토 없는 자동 입고는 안전하지 않습니다.

확인된 권장 흐름:

```text
OCR
→ 영수증 유형 판별
→ 상품·할인·환불 라인 구조화
→ 상품 후보 매칭
→ 모호한 필드만 사용자 확인
→ atomic stock commit
```

세 영수증 모두 개별 식품의 소비기한을 포함하지 않습니다. 재고 반영 후 포장 라벨 촬영 또는 사용자 입력이 추가로 필요합니다.

## 실행 환경과 경계

- 실행일: 2026-09-01
- OS: macOS 27.0, build 26A5388g
- OCR: macOS Vision `VNRecognizeTextRequest`, accurate, `ko-KR` + `en-US`
- Swift: Apple Swift 6.3.3
- Tesseract: 설치 안 됨
- PaddleOCR: 설치 안 됨
- 상품 조회: Open Food Facts API v3.6, 15개 13자리 코드
- 이미지 전처리: 하지 않음
- 원본 이미지: 프로젝트에 복사하지 않음. 임시 첨부 경로에서 읽기 전용으로 검사

이 결과는 PaddleOCR·invoice2data·최종 Rescue Meal parser의 성능 증거가 아닙니다. OCR 가능성과 주요 실패 형태를 확인한 초기 spike입니다.

## 샘플 1 — 식자재마트 영수증

### 확인된 것

- OCR text observation: 65개
- 매장명과 계산대 번호 인식
- `001`~`010` 품목 구간 모두 인식
- 상품명 10개 중 9개는 바로 식별 가능한 수준
- `하림 IFF 냉동가슴살`이 `냉동가습살`로 오인식됨
- 대부분의 단가·수량·금액 및 숫자 코드를 인식
- 일반 13자리 바코드와 `2200...`, `201344` 같은 매장 내부 코드가 혼재

### 실패·위험

- 판매일 `18-01-30`의 구분자가 `~` 등으로 오인식됨
- 일부 수량 `1`이 누락되거나 세로선으로 인식됨
- 한 상품 코드에서 자릿수 누락 가능성이 보임
- 종이의 기울기·접힘으로 같은 행의 이름·단가·수량·금액 연결이 흔들림
- `냉동` 문구가 있는 상품은 냉동 보관을 제안할 수 있지만 실제 사용자의 보관 위치는 확인이 필요함

### 제품 판정

`grocery_receipt` 후보로 자동 분류할 수 있습니다. 모든 행을 draft로 만든 뒤 날짜·수량·내부 코드 항목은 review queue에 남겨야 합니다.

## 샘플 2 — 주류·음료 판매 영수증

### 확인된 것

- OCR text observation: 83개
- 판매일 `25-10-24 13:38`과 계산대 인식
- `001`~`010` 상품 구간 모두 인식
- 상품 바코드·단가·금액을 대부분 인식
- `$특매할인` 라인과 음수 금액을 별도 text line으로 인식
- 상품별 할인 금액이 바로 다음 라인에 붙는 구조가 반복됨

### 실패·위험

- 일부 수량이 누락되어 단가와 합계만 남음
- `$특매할인`이 한 곳에서 `$특매합인`으로 오인식됨
- 할인 라인을 독립 상품으로 처리하면 음수 재고가 생성됨
- 같은 영수증 안에서도 상품명이 한 줄 또는 두 줄로 갈라짐
- 음료·주류는 실온과 냉장 모두 가능하므로 영수증만으로 실제 보관 위치를 알 수 없음

### 제품 판정

`retail_beverage_receipt` 후보입니다. 할인 라인은 선행 상품의 가격 adjustment로 연결하고 StockLot을 만들지 않아야 합니다.

## 샘플 3 — 식당 영수증 + 겹친 카드전표

### 확인된 것

- OCR text observation: 53개
- 계산일자·시간·테이블 번호·주문담당자·결제 합계를 인식
- 보이는 메뉴명과 수량·가격 상당 부분 인식
- 해상도가 510×512로 낮아도 주요 본문을 읽음

### 실패·위험

- 뒤에 겹친 카드전표의 텍스트가 본 영수증 결과에 섞임
- 카드·승인 관련 결제정보가 함께 추출됨
- 한 메뉴명은 원본부터 가려져 있어 복원이 불가능함
- 상품 바코드가 없고 조리된 식당 메뉴이므로 식료품 구매 재고로 넣어서는 안 됨

### 제품 판정

`restaurant_receipt`로 분류해 기본적으로 inventory import 대상에서 제외해야 합니다. 사용자가 남은 음식을 등록하려는 경우에만 별도의 `leftover quick add` 흐름으로 전환합니다.

## Open Food Facts 조회 결과

영수증에서 OCR로 읽힌 13자리 코드 15개를 공식 API v3.6으로 조회했습니다.

| 결과 | 개수 | 의미 |
|---|---:|---|
| API success | 5 | 레코드가 존재함 |
| 구체적 product name 존재 | 4 | 제품명 후보로 바로 사용 가능 |
| product name 공란·brand만 존재 | 1 | 부분 후보만 제공 가능 |
| API failure | 10 | 레코드 없음 |

성공 예:

- `8801045426204`: Ottogi, `Panure Panko`
- `5000267024202`: Johnnie Walker, `Black label`
- `4901004006813`: Asahi 500ml 제품명
- `6901035603232`: Tsingtao 500ml 제품명

부분 성공:

- `8801043014830`: status success이나 product name이 비어 있고 brand 정보만 존재

이 15개 샘플에서는 Open Food Facts를 단독 상품 master로 사용할 수 없습니다. 영수증 OCR 이름, 사용자 확인 별칭, 로컬 상품 사전이 우선이며 Open Food Facts는 보조 enrichment로 취급해야 합니다.

## 설계에 반영할 변경

1. 영수증 유형 classifier를 inventory commit보다 먼저 둡니다.
2. `product`, `discount`, `refund`, `subtotal`, `payment`, `unknown` 라인 타입을 유지합니다.
3. 매장 내부 코드는 GTIN으로 간주하지 않고 `store_internal_sku`로 저장합니다.
4. 상품명·숫자 코드·공간 좌표를 함께 사용해 행을 묶습니다.
5. 누락 수량을 단가=합계라는 이유만으로 무조건 `1`로 확정하지 않습니다.
6. 사용자 확인 결과를 `store + raw_name → product` 별칭으로 학습합니다.
7. 식당 영수증은 자동 제외하고 leftover 등록으로만 전환합니다.
8. 영수증에는 소비기한이 없으므로 입고 후 날짜·보관 확인 task를 생성합니다.
9. 영수증 원본의 결제·회원정보는 inventory에 필요하지 않으므로 보존하지 않습니다.
